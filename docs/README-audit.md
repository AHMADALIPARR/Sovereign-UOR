# Audit of the original README, the sources and the data

This audit covers the repository as of commit `5db9b38`, before any change
made during the audit. The README of that commit is kept verbatim in
[`README-original.md`](README-original.md); references of the form
`README-original.md:N` point at its lines. Source references point at files
under `montrepol/` and `src/`, which are unchanged since `5db9b38`. Licence
statements are outside the scope of this audit.

Corrected versions never replace an original file. They sit beside it with a
`_checked` suffix: the whole Haskell tree as `montrepol_checked/`, and the
oracle as `montrepol/oracles/zeta-zeros-odlyzko_checked.txt`.

Every number below was measured on the build machine (GHC 9.10.1, cabal
3.12.1.0, Scala 3.5.2 with Java 21) or read from a GitHub Actions log.

## 3. Truncation and compile audit

Every file was checked for a missing final newline, an ending in the middle of
a statement or block, placeholder text, references to undefined names, and
whether it compiles.

- No file ends without a newline or in the middle of a statement.
- Placeholders in code (`git grep placeholder`):
  `montrepol/packages/mp-analytic/src/MP/ExplicitFormula.hs:14`,
  `MP/Primes.hs:33`, `MP/Zeta.hs:40`.
- Undefined references: `montrepol/packages/mp-gate/app/Mutants.hs:25`
  (`docArrays`), `:35` (`lookupStrings`), `:36` (`lookupString`);
  `mp-analytic/test/Main.hs:14` uses `vonMangoldtExact`, which `MP/Primes.hs:2-7`
  does not export; `mp-linalg/test/Main.hs:26` uses `%` without importing
  `Data.Ratio`; the linalg tests compare matrices with `===`, which needs a
  `Show (Matrix a)` instance that does not exist.
- Compile errors from `cabal build all --keep-going` (GHC 9.10.1):
  - `mp-linalg/src/MP/Algebra.hs:107`: duplicate instance `Eq (Maybe a)`.
  - `mp-analytic/src/MP/Bernoulli.hs:8`, `MP/Primes.hs:10`,
    `mp-lie/src/MP/RootSystem.hs:17-18`: module from `mp-linalg` not found
    (missing from `build-depends`).
  - `mp-gate/src/MP/Gate/Scan.hs:16` name shadowing, `:22` partial `head` and
    `last`, `:27` and `:35` type defaulting; `Toml.hs:50` name shadowing. All
    are errors because `cabal.project:25` sets `-Werror`.
- Errors found by reading, behind the first ones: `Algebra.hs` `isZero` uses
  `==` without an `Eq` constraint; `Matrix.hs` issues listed at
  `README-original.md:111` above; the mp-gate test file applies `<>` to a
  `SourceFile` constructor argument with the wrong precedence
  (`mp-gate/test/Main.hs:50`); the TOML reader accepts a lone `[`.

Reconstruction: `montrepol_checked/` is a complete copy of `montrepol/` with
every module rewritten where needed. It builds with no warnings under the same
`-Werror` flags, runs 80 tests that all pass (mp-check 5, mp-linalg 19,
mp-lie 13, mp-seq 8, mp-analytic 12, mp-gate 23), reports
`mp-gate: R1-R6 hold over 6 packages`, and catches 10 of 10 mutants. The
gate's checks run over the original tree give 17 violations: R2 for the
unknown authority `steele-2014`, R3 for the untested ID `AN-06`, and 15 R5
uses of partial functions (`Zeta.hs:18`, `Scan.hs:22`, `mp-lie/test/Main.hs:20,21,22,25,26`,
`Matrix.hs:45,60,71,107,146,169`, `mp-linalg/test/Main.hs:79,80`).

## 5. Fabrication audit

### 5.1 `montrepol/oracles/zeta-zeros-odlyzko.txt`: fabricated in large part

Reference: LMFDB, https://www.lmfdb.org/zeros/zeta/list?N=1&limit=600, values
with about 30 decimals, rounded exactly to 10 decimals. Odlyzko's site
(`www-users.cse.umn.edu`) and web.archive.org could not be reached from the
build machine or from the fetch service.

| Measurement | Value |
|---|---|
| Rows | 512 (the count is right) |
| Rows that differ from LMFDB | 426 |
| ... in the last digit only | 7 |
| ... by 1e-10 to 1e-6 | 22 |
| ... by 1e-6 or more | 397 |
| Rows that agree | 1 to 38 and 508 to 512, plus 43 scattered rows |
| Rows wrong by 1e-6 or more | every row from 130 to 507, and rows 71, 90, 103, 106, 108-110, 112-114, 116-122, 124, 126 |
| Rows whose 10 decimals are exactly `8765432109`, `2345678901`, `9876543210` or `1234567891` | 320, from row 188 to row 507 |
| Rows 135 and 136 | both `295.8131297355` (LMFDB: 294.9653696193 and 295.5732548790) |
| Values above 826.91 | 22, largest `858.1234567891` (row 507; LMFDB 820.7218984439). The ledger itself bounds the table at 826.91 (`ledger.toml:14`). |
| Places where the sequence does not increase | rows 136 and 508 |

An independent check: the zero finder in `montrepol_checked` (Hardy Z from a
complex Euler–Maclaurin zeta and a corrected theta, scan step 0.05, bisection
to 1e-11) finds exactly 512 zeros on (10, 827]. Against the original table,
408 of them differ by 1e-8 or more, the largest difference being 37.78. Against
the LMFDB-based `zeta-zeros-odlyzko_checked.txt`, none does; the largest
difference is 5.3e-11. AN-06 in `montrepol_checked` runs this comparison.

Verdict: fabricated (426 wrong rows, digit patterns, a duplicated value, values
outside the stated range). The header's provenance (Odlyzko's `zeros1`, copied
via another repository) is unverifiable from here.
